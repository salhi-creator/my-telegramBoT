# Telegram Bot

A Telegram bot built with Node.js and TypeScript, using a webhook-based architecture and Redis for caching and fast-access data.

## How It Works

The bot communicates with Telegram through a **webhook** rather than continuously polling Telegram for updates.

The general request flow looks like this:

```text
Telegram
   │
   │  User sends a message
   ▼
Telegram Bot API
   │
   │  HTTPS POST
   ▼
Your Server
   │
   ├── Process Telegram update
   │
   ├── Read / update cached data
   │          │
   │          ▼
   │       Redis
   │
   └── Generate response
          │
          ▼
     Telegram Bot API
          │
          ▼
        User
```

### 1. User interacts with the bot

A user sends a message or performs an action inside Telegram.

Telegram creates an **Update** containing information about the event.

For example:

```json
{
  "update_id": 123456789,
  "message": {
    "chat": {
      "id": 123456789
    },
    "text": "/start"
  }
}
```

### 2. Telegram sends the update to the server

Because the bot uses a webhook, Telegram sends an HTTP `POST` request to the webhook endpoint configured for the bot.

For example:

```text
POST https://your-domain.com/telegram/webhook
```

Your server receives the update and passes it to the bot's application logic.

### 3. The server processes the update

The server determines what the user wants to do and executes the appropriate bot logic.

Depending on the command or event, the bot may:

* Process a Telegram command
* Read user information
* Store state
* Retrieve cached information
* Call external APIs
* Generate a response
* Send a message back to Telegram

### 4. Redis is used for fast-access data

Redis is used as a cache and temporary data store.

This is useful for information that needs to be accessed frequently without repeatedly querying a slower persistent data source.

The application connects to Redis using environment variables rather than hardcoding credentials.

# Requirements

Before running the bot, you need:

* Node.js
* npm
* A Telegram bot created through **BotFather**
* A Redis instance

For local development, you will also need a way to expose your local server to the internet, such as a tunneling service.

# Environment Variables

Create a `.env` file in the root of the project.

Example:

```env
TELEGRAM_BOT_TOKEN=your_telegram_bot_token

REDIS_URL=your_redis_connection_url

REDIS_LANG_CACHE=your_redis_credential

WEBHOOK_URL=https://your-domain.com

WEBHOOK_PATH=/telegram/webhook

PORT=3000
```

> The exact variable names depend on the implementation. Use the names expected by the application's configuration.

## What These Variables Do

### `TELEGRAM_BOT_TOKEN`

The authentication token generated by Telegram's **BotFather**.

It allows the application to communicate with the Telegram Bot API.

Example:

```env
TELEGRAM_BOT_TOKEN=123456789:AAxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**Never commit this token to GitHub.**

---

### `REDIS_URL`

The connection URL used by the application to connect to Redis.

Example:

```env
REDIS_URL=redis://username:password@host:6379
```

Depending on the Redis provider, the URL may use TLS:

```env
REDIS_URL=rediss://username:password@host:6379
```

---

### `REDIS_LANG_CACHE`

Credential/configuration used by the language/cache component of the application.

Keep this value private.

Do **not** place the real value inside this README.

---

### `WEBHOOK_URL`

The public HTTPS address where your server is running.

Example:

```env
WEBHOOK_URL=https://bot.example.com
```

Telegram must be able to reach this address from the internet.

---

### `WEBHOOK_PATH`

The endpoint where Telegram sends bot updates.

Example:

```env
WEBHOOK_PATH=/telegram/webhook
```

The complete webhook URL would therefore be:

```text
https://bot.example.com/telegram/webhook
```

---

### `PORT`

The port used by the Node.js server.

Example:

```env
PORT=3000
```

# Connecting Telegram to the Webhook

Telegram needs to know where your server should receive updates.

The webhook is registered through the Telegram Bot API.

The general API request is:

```text
https://api.telegram.org/bot<BOT_TOKEN>/setWebhook?url=<WEBHOOK_URL>
```

For example:

```text
https://api.telegram.org/botYOUR_BOT_TOKEN/setWebhook?url=https://bot.example.com/telegram/webhook
```

Replace:

```text
YOUR_BOT_TOKEN
```

with your bot token and:

```text
https://bot.example.com/telegram/webhook
```

with your actual public webhook endpoint.

## Using cURL

You can register the webhook from a terminal:

```bash
curl -X POST "https://api.telegram.org/botYOUR_BOT_TOKEN/setWebhook" \
  -d "url=https://bot.example.com/telegram/webhook"
```

A successful request should return a response similar to:

```json
{
  "ok": true,
  "result": true,
  "description": "Webhook was set"
}
```

# Checking the Webhook

Telegram provides an API endpoint that shows the current webhook configuration.

```text
https://api.telegram.org/bot<BOT_TOKEN>/getWebhookInfo
```

Using cURL:

```bash
curl "https://api.telegram.org/botYOUR_BOT_TOKEN/getWebhookInfo"
```

This can help diagnose problems such as:

* Incorrect webhook URL
* Server unavailable
* Invalid SSL certificate
* Telegram being unable to reach the server
* Updates failing to be delivered

---

# Webhook Requirements

Telegram must be able to reach your webhook server.

Your production server should therefore have:

* A public IP/domain
* HTTPS
* A valid SSL/TLS certificate
* The webhook route exposed publicly
* The bot server running continuously

A local address such as:

```text
http://localhost:3000
```

cannot normally be used directly by Telegram because Telegram's servers cannot access your computer's localhost.

For local development, you can expose the server through a tunneling service and use the generated HTTPS URL as the webhook.

---

# Webhook Security

The webhook endpoint should not blindly trust every incoming request.

Telegram supports a webhook secret token that can be used to verify requests.

For example, when registering the webhook:

```bash
curl -X POST "https://api.telegram.org/botYOUR_BOT_TOKEN/setWebhook" \
  -d "url=https://bot.example.com/telegram/webhook" \
  -d "secret_token=YOUR_WEBHOOK_SECRET"
```

Your server can then verify the corresponding Telegram request header before processing the update.

The secret should also be stored in `.env`:

```env
TELEGRAM_WEBHOOK_SECRET=your_secret
```

Never hardcode it in the source code.

# Project Architecture

A typical request moves through the application like this:

```text
                    ┌─────────────────┐
                    │     Telegram    │
                    └────────┬────────┘
                             │
                             │ HTTPS POST
                             ▼
                    ┌─────────────────┐
                    │  Webhook Route  │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Bot Controller │
                    └────────┬────────┘
                             │
                ┌────────────┼────────────┐
                │            │            │
                ▼            ▼            ▼
             Commands      Redis       Services
                │            │            │
                └────────────┼────────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ Telegram Bot API│
                    └────────┬────────┘
                             │
                             ▼


                       User
```


This separates the Telegram transport layer from the actual application logic.

# Security

Environment variables contain sensitive credentials.

**Never commit `.env` to Git.**

Your `.gitignore` should contain:

```gitignore
.env
.env.*
!.env.example
```

Instead of committing the real configuration, create an example file:

```text
.env.example
```

Example:

```env
TELEGRAM_BOT_TOKEN=
REDIS_URL=
REDIS_LANG_CACHE=
WEBHOOK_URL=
WEBHOOK_PATH=/telegram/webhook
TELEGRAM_WEBHOOK_SECRET=
PORT=3000
```

This shows other developers what configuration is required without exposing your credentials.

# Troubleshooting

## Bot does not respond

Check that:

1. The server is running.
2. The webhook URL is correct.
3. The webhook uses HTTPS.
4. Telegram can reach the server.
5. The bot token is correct.
6. Redis is reachable.
7. The webhook route matches the configured path.

Check the webhook information:

```bash
curl "https://api.telegram.org/botYOUR_BOT_TOKEN/getWebhookInfo"
```

---

## Redis connection fails

Check:

```env
REDIS_URL=
REDIS_LANG_CACHE=
```

Make sure the Redis credentials are correct and that your server is allowed to connect to the Redis instance.

---

## Telegram cannot reach the webhook

Make sure the webhook URL is publicly accessible.

This will **not** work:

```text
http://localhost:3000/telegram/webhook
```

You need something similar to:

```text
https://your-domain.com/telegram/webhook
```

## Changing the Bot's Behaviour

The bot's behaviour and instructions are defined in the `instructions.txt` file.

If you want to change **how the bot behaves, responds, or follows instructions**, modify:

```text
instructions.txt
```

The application loads the instructions from this file and uses them when processing interactions.

### Examples of things you can change

You can modify `instructions.txt` to change:

* The bot's personality and tone
* How it responds to users
* Rules the bot should follow
* What it should or should not do
* Response style and formatting
* How it handles particular situations
* Additional behavioural instructions

For example:

```text
You are a helpful and concise Telegram assistant.

Always keep responses short and easy to understand.

If the user asks about X, respond according to Y.

Do not discuss Z.
```

After modifying `instructions.txt`, restart the application if the file is only loaded when the server starts.

> **Important:** You normally do not need to modify the bot's TypeScript/JavaScript logic just to change its behaviour. Start with `instructions.txt`. Code changes are only necessary when changing the bot's actual functionality or architecture.
